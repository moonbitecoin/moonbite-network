Infrastructure

Don't trust. Verify.

A full node validates every transaction and block against the protocol rules — independently, on your own hardware. No third party required. When you run a node you're not relying on anyone else's word about the state of the chain.

Setup Guide MoonBite Core
Why run a node

What a full node does for you

🔎

Verify your own balance

Your node keeps a full copy of the UTXO set. You don't need to ask a block explorer — you can query your own node directly and know the answer is right.

🛡️

Enforce the rules yourself

Your node rejects any block or transaction that violates the consensus rules — invalid signatures, double spends, blocks over the size limit. It does this independently, not on the word of another node.

🌐

Strengthen the network

Every additional node makes the chain harder to censor or rewrite. Transactions you broadcast go to the peer-to-peer network directly — no intermediary can silently drop them.

⛏️

Mine to your own node

If you mine, pointing your miner at your own node means you're building on a chain you've verified yourself — not trusting a remote endpoint you don't control.

🔌

Use the read-only API

The node exposes a local REST API for block and transaction queries. Build tools, scripts, or integrations against your own chain data with no rate limits or third-party dependencies.

API reference →
📡

Relay transactions

A node relays valid transactions to its peers. The more honest relay nodes there are, the faster a legitimate transaction reaches miners and gets confirmed.

What you need

Requirements — no special hardware

A modest general-purpose machine is enough. MoonBite is still early, so the chain is small.

💻

Hardware

Any reasonably modern desktop, laptop, or small server. The node process is light during normal operation — initial block download (IBD) is heavier but temporary.

💾

Disk

The full chain data grows as the chain matures. On a young network the footprint is small. An SSD improves IBD speed noticeably, but a standard hard drive works.

🌐

Bandwidth

A stable broadband connection is all you need. The node uses bandwidth proportional to how many peers it connects to and how much transaction traffic flows. It is not a high-bandwidth workload during normal operation.

🔒

Ports

The default peer-to-peer port should be reachable from the internet for you to contribute inbound connections to the network. Firewalling is your choice — a node behind NAT still validates locally.

🐧

Operating system

Linux (including WSL), macOS, and Windows are all supported. The reference implementation follows Litecoin Core lineage and builds cleanly on all three platforms.

⏰

Uptime

A node is most useful when it stays online. Even modest uptime helps the peer-to-peer graph. The node picks up where it left off when restarted — no resync from scratch.

Getting started

How to run a node

Full step-by-step instructions live in the developer docs and README. Here's a quick orientation.

📥

1 — Get the software

Clone or download the MoonBite Core source from GitHub, or grab a pre-built binary from the releases page. Verify the checksum before running anything.

MoonBite Core on GitHub →
📄

2 — Read the README

The README covers build dependencies, configuration options, and how to start the node on mainnet, testnet, or regtest. Start with regtest to try things safely before joining the live network.

README.txt →
⚙️

3 — Configure and start

A minimal config file is all you need to get going. The developer docs include an annotated example. Once started the node connects to peers, downloads the chain, and begins validating.

Developer setup guide →
🖥️

4 — Query your node

Once synced, the local REST API is available for block and transaction queries. You can also point the MoonBite wallet at your own node to avoid relying on the public seed node.

API reference →
Example

Starting the node & querying the API

These are illustrative examples. Actual flags and paths depend on your build and config — see the README for the full reference.

# Start the node on testnet (safe to experiment)
./moonbited -testnet -daemon

# Check sync status via the read-only REST API (local node)
curl http://127.0.0.1:19444/api/status

# Query a block by height
curl http://127.0.0.1:19444/api/block/1

# Query the UTXO balance for an address
curl http://127.0.0.1:19444/api/address/tmoon1youraddresshere
